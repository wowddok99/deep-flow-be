# ADR-004. 분산 락 획득 후 트랜잭션 본문을 실행한다

## 상태

Accepted

## 배경

세션 시작, 크루 가입, 세션 공유, Outbox worker 실행은 동시에 같은 자원에 접근하면 중복 생성이나 정원 초과, 중복 처리 문제가 생길 수 있습니다.

단순히 메서드에 `@Transactional`과 분산 락을 함께 붙이면 트랜잭션 시작 시점과 락 획득 시점의 순서가 흐려질 수 있습니다. 락 해제 전에 커밋이 끝나지 않으면 다른 요청이 미커밋 상태를 기준으로 검증을 통과할 위험이 있습니다.

## 결정

`DistributedLockAop`에서 락을 먼저 획득하고, `AopForTransaction#proceed`를 통해 락 안에서 트랜잭션 본문을 실행합니다.

락 경계가 중요한 유스케이스는 별도 Locker 빈을 둡니다.

- `CrewJoinLocker`
- `SessionShareLocker`
- `OutboxWorkerLocker`

## 결과

장점:
- 락 획득 전 트랜잭션 시작을 피할 수 있음
- 커밋 전 락 해제로 인한 경쟁 조건을 줄일 수 있음
- 크루 최대 인원, 세션 공유 중복, Outbox 중복 처리 같은 불변 조건을 보호하기 쉬움

단점:
- 유스케이스 진입점과 실제 트랜잭션 본문이 분리되어 코드 경로가 길어짐
- Locker를 거치지 않고 내부 메서드를 직접 호출하면 락 보호가 깨질 수 있음
- Redisson/Redis 장애가 해당 유스케이스 실패로 이어질 수 있음
